# 加密文件格式规范（1.4.0 起冻结）

> **状态：自 2026-11-11（1.4.0）起冻结。** 本文描述 Android 与桌面端共同读写的 `.aegix` 单文件容器与外部分卷容器；容器版本 1 的字节布局与语义是 1.x 的兼容基准，不包含旧格式。
> 版本、测试计数与验收结论只看[项目现状报告](android/项目现状报告与交接指南.md)。旧格式删除范围见[去兼容盘点与格式冻结清单](去兼容盘点与格式冻结清单.md)。
> 代码事实来源：`shared/crypto-core` 的 `FileCryptoEngine`、`SignedAndEncryptedData`、`Encryptor`、`VolumePartWriter`、`VolumeCryptoEngine`、`VolumeInfoParser`、`VolumePartPlan`。Android 与桌面都依赖这份共享内核；格式变更必须同时跑两端测试。

## 0. 一句话结论

当前只有两种线格式：**单文件容器**和**外部分卷容器**。外部分卷的每一卷本身就是一个完整的单卷容器，因此两种格式共用同一段单文件布局；分卷的外层文件名只含时间戳、集合短码和卷号，原始文件名只出现在加密元数据里。

## 1. 通用约定

| 项 | 约定 |
|---|---|
| 字节序 | 大端序（Java `ByteBuffer.putInt` / `KeyUtils.intToBytes`） |
| 长度字段 | 4 字节有符号整数，单位是字节；解析时必须做上下界检查 |
| 对齐/填充 | 无；字段首尾相接 |
| 字符串编码 | UTF-8 |
| 魔数 | ASCII `VOLU`，即 `0x564F4C55` |
| 容器版本 | 当前只支持 `1`；其他版本明确拒绝，不猜、不回退 |
| 认证加密 | AES-256-GCM，12 字节 IV，16 字节 tag；密文字段包含 tag |
| 文件密钥包装 | RSA-OAEP，主摘要 SHA-256，MGF1 摘要 SHA-1，空 PSource |
| 签名 | SHA256withRSA，对**明文**签名 |
| 内容哈希 | SHA-256，小写十六进制；比较时忽略大小写 |

`OaepCompat` 里的“SHA-256 + MGF1-SHA1”不是旧版本兼容，而是桌面 JDK 与 Android Conscrypt 的 Provider 差异兼容层。去掉它会导致两端互相解不开文件密钥。

## 2. 单文件容器

### 2.1 字节布局

| 顺序 | 字段 | 长度 | 说明 |
|---:|---|---:|---|
| 1 | `signatureLength` | 4 | 签名字节数，`1..10240` |
| 2 | `signature` | 变长 | `SHA256withRSA` 对明文签名 |
| 3 | `fileNameIvLength` | 4 | 文件名 IV 字节数；无文件名时为 `0`，当前为 `12` |
| 4 | `fileNameIv` | 变长 | 文件名 AES-GCM 的 IV |
| 5 | `encryptedFileNameLength` | 4 | 加密文件名字节数，`0..4096`；无文件名时为 `0` |
| 6 | `encryptedFileName` | 变长 | 原始文件名 UTF-8 的 AES-GCM 密文（含 16 字节 tag） |
| 7 | `encryptedKeyLength` | 4 | RSA 包装的文件 AES 密钥字节数，`1..1024` |
| 8 | `encryptedKey` | 变长 | 用接收方公钥做 RSA-OAEP 的 AES-256 密钥 |
| 9 | `aesIvLength` | 4 | 内容 AES-GCM IV 字节数，`1..128`，当前为 `12` |
| 10 | `aesIv` | 变长 | 内容加密 IV |
| 11 | `ciphertextLength` | 4 | 内容密文字节数，至少 16（GCM tag） |
| 12 | `ciphertext` | 变长 | AES-256-GCM 密文 + 16 字节 tag |

### 2.2 语义

- **签名对象是明文**，不是密文。解密后先用发送方公钥验签；签名不匹配不阻止写出明文，但结果必须标记“发送者未识别”。
- **文件 AES 密钥是随机生成的 256 位密钥**，只被接收方公钥包装一次；同一文件的文件名加密和内容加密使用同一把文件密钥，但各自使用独立 IV。
- **原始文件名只存在于第 5/6 字段的加密内容中**；外层文件名、明文文件头、日志、通知和分享意图都不得出现原始文件名。
- 当前写入方：Android 与桌面都走 `FileCryptoEngine.encrypt`，写出同一套字节；桌面不再走 `SignedAndEncryptedData` + `Encryptor` 的整文件内存路径。
- 单文件明文上限：`Integer.MAX_VALUE - 16` 字节（32 位密文长度字段的限制）。超过用户选择的单卷上限时，两端都改为“单文件直接切片写外部分卷”，每卷内部仍是本布局；不再把普通文件包成 ZIP。

### 2.3 扩展名

扩展名不是密码学格式的一部分：

- Android 与桌面当前都只写 `.aegix`。
- 两端都只把 `.aegix` 当作密文后缀；`.enc` 不再识别、不再展示，也不会阻止普通文件被加密。
- 扩展名不参与线格式校验；真正的判型仍看文件头结构。

## 3. 外部分卷容器

### 3.1 每一卷的布局

每一卷都是独立的单卷容器，文件本身可以直接交给 `VolumeCryptoEngine.decrypt`：

| 顺序 | 字段 | 长度 | 说明 |
|---:|---|---:|---|
| 1 | `magic` | 4 | ASCII `VOLU` |
| 2 | `version` | 4 | 当前为 `1` |
| 3 | `metadataLength` | 4 | 加密 `VolumeInfo` 的字节数，`1..1048576` |
| 4 | `encryptedMetadata` | 变长 | `Encryptor.EncryptedData` 字节；解密后是 UTF-8 JSON |
| 5 | `innerContainer` | 变长 | 一个完整的单文件容器（§2），明文是本卷切片 |

**注意**：第 3 个 4 字节字段是 `metadataLength`，不是 `FileFormatHeader.algorithmId`。`FileFormatHeader` 是一个通用的 12 字节头类，第三字段在旧代码里叫 `algorithmId`；VOLU 写入器复用了它的 `MAGIC`/`CURRENT_VERSION`/`HEADER_SIZE`，但按“元数据长度”写入。解析时必须按本规范读，不能调用 `FileFormatHeader.readFrom` 后把第三字段当算法 ID。

`encryptedMetadata` 是标准 `Encryptor.EncryptedData`：

```
[encryptedKeyLength 4][RSA-OAEP 加密的 AES 密钥][ivLength 4][AES-GCM IV][cipherLength 4][AES-GCM 密文+tag]
```

元数据明文是 `VolumeInfo` 的 JSON；元数据没有独立签名，安全性来自 RSA 只有接收方能解、以及每卷内部单文件容器的 GCM/签名/哈希校验。接收方必须把元数据当作不可信输入，按 §4 的规则逐字段校验。

### 3.2 单卷与多卷

- 每一卷的 `VolumeInfo.volumeCount` 固定为 `1`；`encryptedVolumeSizes` 恰好一个元素，值等于本卷 `innerContainer` 的字节数。
- 多卷的顺序由 `VolumeInfo.partIndex` 决定，**不是**由外层文件名或用户选择顺序决定。
- `partCount` 范围 `1..99`；`partIndex` 范围 `1..partCount`。
- 单卷包（`partCount=1`）仍然是外部分卷：它携带完整的 `setId/partIndex/partCount/archive*` 字段，不是旧内部 VOLU。
- 多卷包的每一卷 `sourceIsFolder` 必须为 `false`；只有单卷包可以保留文件夹语义。

### 3.3 每卷内部单文件容器的逻辑名

写入器为每卷构造一个内部单文件容器，其 `originalFileName` 不是用户原始文件名，而是本卷的逻辑名：

| 场景 | `VolumeInfo.originalFileName` | 内部容器里的加密文件名 |
|---|---|---|
| 单卷包 | `archiveName`（如 `季度 报告.zip`） | `archiveName + ".part1"` |
| 多卷包第 N 卷 | `archiveName + ".partNNN"` | 上一列再 `+ ".part1"` |

`VolumeCryptoEngine` 会校验内部容器的文件名是否等于 `VolumeInfo.originalFileName + ".part" + partNumber`，因此卷号、元数据和内部容器三者是绑定的；换序、改名或缺卷都会在解密阶段被发现。

## 4. VolumeInfo JSON

### 4.1 字段

| 字段 | 类型 | 当前外部分卷 | 约束与语义 |
|---|---|---|---|
| `originalFileName` | string | 必有 | 本卷逻辑名；非空、≤1024 字符、无 ISO 控制字符 |
| `originalFileSize` | long | 必有 | 本卷明文切片字节数（ZIP 或原文件），`>0` |
| `volumeCount` | int | 必有 | 外部分卷固定为 `1` |
| `volumeSize` | long | 必有 | 本卷明文容量/大小；外部分卷必须等于 `originalFileSize` |
| `sourceIsFolder` | boolean | 必有 | 单卷包且原始来源是文件夹时为 `true`；多卷包必须为 `false` |
| `sha256Hash` | string | 当前写入器必写 | 本卷明文的 SHA-256；解析器允许缺省，但外部分卷写入器总是写 |
| `createdAt` | string | 当前写入器必写 | 供人看的创建时间；≤256 字符；不参与校验 |
| `encryptedVolumeSizes` | long[] | 必有 | 外部分卷恰好 1 个元素，等于本卷内部容器字节数 |
| `setId` | string | 必有 | 同一批分卷共享的随机 ID；非空、≤128 字符、无控制字符 |
| `partIndex` | int | 必有 | 1-based 卷号，`1..partCount` |
| `partCount` | int | 必有 | 总卷数，`1..99` |
| `archiveName` | string | 必有 | 还原目标的叶子文件名：归档为 ZIP 名，单文件分卷为原文件名；非空、≤1024 字符、无 `/`、`\`、控制字符，且不能是 `.`/`..` |
| `archiveSize` | long | 必有 | 整包（ZIP 或原始文件）字节数，`>0` |
| `archiveSha256` | string | 必有 | 整包 SHA-256，64 位十六进制 |
| `archiveSourceIsFolder` | boolean | 必有 | 原始来源是否为文件夹 |
| `sourceIsArchive` | boolean | 必有 | `true`：合并结果是 ZIP；`false`：单文件切片，合并结果直接是原文件 |
| `sourceFileCount` | int | 必有 | ZIP 内文件条目数（不含目录），`0..1000000`；`sourceIsArchive=false` 时必须为 `1` |

### 4.2 解析规则

- JSON 最大 1 MiB，嵌套深度最大 8；重复字段直接拒绝；字段类型必须严格匹配；末尾多余内容拒绝。
- 未知字段跳过，为未来加字段留余地；但改变已有字段语义必须先升容器版本。
- 九个外部分卷集合字段（`setId` 到 `sourceFileCount`）必须**全有或全无**；只出现半套直接拒绝。
- `archiveSize` 不得小于 `originalFileSize`；`partCount=1` 时必须相等。
- `partCount>1` 时 `sourceIsFolder` 必须为 `false`；`partCount=1` 且 `sourceIsFolder=true` 时 `archiveSourceIsFolder` 必须为 `true`。
- `sourceIsArchive=false` 时 `sourceFileCount` 必须为 `1`，且 `archiveSourceIsFolder`、`sourceIsFolder` 都必须为 `false`。
- `volumeCount` 必须为 `1`；`volumeSize` 必须等于 `originalFileSize`；`encryptedVolumeSizes` 必须恰好 1 个元素。
- `sha256Hash` 若出现必须是 64 位十六进制；空字符串按缺省处理。
- `archiveName` 和 `originalFileName` 只做“叶子名”校验；接收方在落盘前仍要按平台规则再做一次文件名清洗，不能直接拼接路径。

### 4.3 当前不接受的旧形态

以下形态不属于当前格式，去兼容阶段会明确拒绝：

- `volumeCount=N`（N>1）且一个文件里装多段分卷的旧内部 VOLU；
- 没有 `setId/partIndex/partCount/archive*` 九个字段的旧 VOLU；
- 没有 `encryptedVolumeSizes` 的旧元数据；
- 纯 `.enc` 后缀 + 旧版本互操作样本。

这些旧形态已被当前代码明确拒绝：旧内部 VOLU 会在解析 `volumeCount` 或缺失外部分卷字段时失败，旧 `.enc` 只按普通文件处理。旧文件不再迁移，也不应再生成。

## 5. 外层命名与文件名隐私

### 5.1 当前命名

| 场景 | 文件名 |
|---|---|
| 单文件/单卷 | `secure_file_<yyyyMMdd_HHmmss>.aegix` |
| 多卷 | `secure_file_<yyyyMMdd_HHmmss>_<setCode>_volNNN.aegix` |

- `setCode` 是 `setId` 前 6 个字符的小写形式；当前 `setId` 由 UUID 生成，因此通常是 6 位十六进制。
- `NNN` 是 3 位补零卷号，从 `001` 开始；最多 99 卷。
- 重名时追加 `_2`、`_3`…，不改变格式。
- 外层文件名不含原始文件名、原后缀、联系人名、路径或内容哈希。

### 5.2 隐私边界

**原始文件名允许出现的位置**：

- 单文件容器的第 6 字段 `encryptedFileName`（加密）；
- 外部分卷的加密 `VolumeInfo` 里的 `originalFileName` / `archiveName`（加密）；
- 解密完成后的明文结果文件名（这是结果本身，不是密文元数据）。

**不得出现的位置**：

- 外层 `.aegix` 文件名；
- VOLU 12 字节头或任何未加密元数据；
- 日志、通知、分享标题、ClipData 标签、进度文案；
- 临时文件名（临时名只用固定前缀 + 随机串）。

Android 侧已有“输出名不含原名”和“原名只进加密头”的测试；桌面侧原来日志直接拼 `file.getName()`、旧分卷写入在原目录落明文 `.partNNN` 的问题已按盘点文档修复。2026-11-09 又补了分享意图、通知、任务日志、桌面日志的自动化断言；格式已于 2026-11-11 冻结，兼容策略见 §11。

## 6. 校验与错误

### 6.1 单卷校验顺序

1. 魔数、版本、元数据长度；
2. RSA 解元数据（错接收方 → `WrongRecipientException`）；
3. `VolumeInfo` JSON 严格解析与字段校验；
4. 内部单文件容器：签名长度/文件名长度/密钥长度/IV 长度/密文长度边界；
5. RSA 解文件密钥（错接收方 → `WrongRecipientException`）；
6. AES-GCM 认证（篡改/截断 → `FileFormatException`）；
7. 明文长度与 `originalFileSize` 一致；
8. 内部文件名与 `originalFileName + ".part" + partNumber` 一致；
9. 本卷明文 SHA-256 与 `sha256Hash` 一致；
10. 文件末尾没有多余数据。

### 6.2 多卷集合校验

- 每卷必须声明 `partCount>1`、`partIndex`、非空 `setId`；
- 同一集合的 `setId`、`partCount`、`archiveSha256`、`archiveName`、`archiveSize` 必须一致；
- 卷号不得重复、不得越界、必须覆盖 `1..partCount`；
- 合并后总字节数必须等于 `archiveSize`，整包 SHA-256 必须等于 `archiveSha256`；
- 任何缺卷、重卷、混包、改名、换序、篡改、截断都必须失败，且不留下半成品输出。

### 6.3 错误类型

| 情况 | 异常 |
|---|---|
| 魔数不对、长度字段越界、JSON 结构错误、卷名/顺序不一致 | `VolumeFormatException` |
| 版本不是 1 | `UnsupportedVolumeVersionException`（带实际版本号） |
| 不是加密给本机私钥 | `WrongRecipientException` |
| 长度/SHA-256/集合一致性不符 | `VolumeIntegrityException` |
| 单文件容器 GCM/长度错误 | `FileFormatException` |
| 用户取消 | `FileCancelledException` |

## 7. 边界与预算

| 项 | 当前值 |
|---|---|
| 单文件明文上限 | `Integer.MAX_VALUE - 16` 字节 |
| 单卷最终大小上限 | 由调用方传入的 `volumeLimitBytes` 决定，必须 `> 4096` |
| 头部预留 | 4096 字节（VOLU 头 + 单文件容器头的预算） |
| 每卷明文容量 | `volumeLimitBytes - 4096` |
| 卷数 | `ceil(archiveBytes / 每卷容量)`，最大 99 |
| ZIP 总量上限 | 4 GiB（`VolumePartPlan.MAX_ARCHIVE_BYTES`，只约束归档来源） |
| 单文件总量上限 | 不设固定 4 GiB 上限；由“每卷容量 × 99 卷”与用户选择共同决定 |
| 元数据上限 | 1 MiB（明文 JSON 与 RSA 密文分别检查） |
| 每卷内部容器长度 | `<= Integer.MAX_VALUE` |

当前写入器在写完每一卷后会重新核对实际文件长度，不能只信预算。“用户设置分卷大小”只改变 `volumeLimitBytes` 的取值，不改变上述布局与字段语义。

## 8. 当前未做/不包含

- **两端单文件自动分卷已接入写入与合并**：普通文件超过所选单卷上限时直接切片，`sourceIsArchive=false`；桌面 `ExternalVolumeWriter` / `ExternalPartMerger` 与 Android `SingleFileVolumePipeline` / `ArchivePartReader` 都已按该字段还原原文件。文件夹来源仍先打包成 ZIP，再按归档语义分卷。
- **分卷大小**：Android 与桌面都由用户设置五档（50/100/500 MB/1/2 GB，默认 500 MB），单文件与文件夹共用；只影响切片预算，不改变外层线格式。设备上的超大文件分卷验收已暂停（2026-11-08）。
- **旧 `.enc` 写入已删除**：两端都不再生成 `.enc`；扩展名统一不是格式变更。
- **旧纯 GCM1 备份**：不属于文件容器格式；当前密钥备份是 `aegix-key-bundle` 文本，内层 GCM1 是当前实现的一部分。
- **旧版互操作**：不承诺旧 APK/旧桌面包读新格式，也不承诺新包读旧格式；旧样本只用于删除前的拒绝测试。

## 9. 夹具与测试

当前固定样本在：

- `shared/crypto-core/src/test/resources/external/`：共享内核测试读取；
- `desktop/src/test/resources/external/`：桌面测试读取同一批字节的副本。

样本由共享内核 `VolumePartWriter` 生成，使用只用于测试的 RSA 密钥，包含：

- 多卷 ZIP：3 卷，每卷独立解密后按卷号拼接，整包 SHA-256 校验；
- 单卷文件夹包：1 卷，保留文件夹语义，元数据里含非 ASCII 归档名；
- 属性文件记录整包名、大小、SHA-256、卷号、文件名和测试密钥。

测试覆盖：

- 每卷元数据字段、签名、本卷哈希、内部文件名绑定；
- 多卷拼接与整包哈希；
- 单卷文件夹语义；
- 外层文件名和密文字节中不出现明文归档名；
- 桌面 `ExternalPartMerger` 读取同一组固定样本并合并出原始 ZIP；
- 错接收方、篡改、截断、换序、缺卷等拒绝路径（共享内核现有测试已覆盖，新增夹具测试至少覆盖正常路径和隐私断言）。

重新生成命令与说明见 `shared/crypto-core/src/test/resources/external/README.md`。夹具更新后必须同时复制到桌面测试资源，并跑两端测试。

单文件容器另有 `shared/crypto-core/src/test/resources/single/`：一份密文与属性文件（公开测试密钥、明文 Base64/大小/SHA-256、签名长度）。单文件容器没有魔数/版本字段，夹具钉住“第一项是签名长度”及其后的长度字段顺序；**未来版本拒绝**只能在有版本字段的 VOLU 上验证：把夹具版本改为 2，必须抛 `UnsupportedVolumeVersionException`，不能按版本 1 猜。

随机变异：两端的解压测试用固定种子篡改合法 ZIP（翻位、清零、截断），只断言“不写出目标目录、不超条目/字节上限”，不把随机字节当成合法格式。

## 11. 兼容策略（冻结后）

1. **1.x 只增不改**：1.4.0 写出的容器版本 1 文件，之后所有 1.x 版本必须能读。
2. **不兼容变更必须升版本**：改变字段含义、顺序、约束或加密参数时，容器版本号必须提升；解析器对未知版本明确拒绝，不猜、不回退。
3. **新字段只能进新版本**：1.x 不得在版本 1 的字节流里追加可选字段，也不得改变现有字段的长度语义。
4. **夹具是回归基准**：`shared/crypto-core/src/test/resources/single/`、`external/` 与两端的固定夹具不得随实现改动；如必须更新，视为不兼容变更。
